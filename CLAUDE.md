# CLAUDE.md - Project Instructions for Claude Code

## Project Overview

pg2any is a Rust CDC (Change Data Capture) library that streams PostgreSQL WAL changes to MySQL, SQL Server, SQLite, or Kafka. Workspace with two crates: `pg2any-lib` (core library) and `examples` (binary).

## Code Conventions

- **Async runtime**: Tokio with `#[tokio::main]` / `#[tokio::test]`
- **Error handling**: `CdcError` enum via `thiserror`, propagated with `?`. Use `CdcError::config()`, `CdcError::generic()`, etc. constructors
- **Traits**: `async-trait` for async trait methods
- **Logging**: `tracing` crate (`info!`, `warn!`, `error!`, `debug!`), no `println!`
- **Feature gates**: All destinations use `#[cfg(feature = "...")]` conditional compilation
- **Naming**: `DestinationType` enum variants are PascalCase (`MySQL`, `SqlServer`, `SQLite`, `Kafka`)
- **Config**: Builder pattern (`Config::builder().field(val).build()`)
- **Tests**: Integration tests in `pg2any-lib/tests/`, unit tests as `#[cfg(test)] mod tests` inline. Snapshot e2e tests (`snapshot_e2e_*.rs`) are `#[ignore]`d and need docker: `make snapshot-test-sqlite|mysql|sqlserver|kafka`, `make snapshot-test` (all four, then clean), `make snapshot-test-clean`, `make snapshot-unit-test` (no services); `make before-git-push` runs the CI checks and then the snapshot unit tests and all four e2e suites (docker, ~25 min); throughput benchmarks `make snapshot-bench-*` (add `SNAPSHOT_BENCH_CARGO_FLAGS=--release`). The regular targets skip `bench_` tests and do not run the final default snapshot settings

## Architecture Rules

- Producer and consumer are separate Tokio tasks communicating via `mpsc` channel
- Transaction files are the source of truth for crash recovery - never skip file persistence (two approved exceptions: the initial-snapshot phase and the always-on in-memory fast path, both below)
- LSN tracking: `flush_lsn` = last WAL position committed to destination. Updated by consumer only (one approved exception: the snapshot completion write, below).
- Recovery resume position (`slot.rs::reconcile_resume`, called from `CdcClient::new`): query `pg_replication_slots` first (server-side `confirmed_flush_lsn` is the source of truth for logical replication resume), fall back to the on-disk LSN when the slot is gone. De-dup boundary = `max(confirmed_flush_lsn, disk_flush_lsn)` — seeds `LsnTracker` so `commit_lsn <= boundary` transactions are skipped (preserves the no-replay guarantee). Slot-deleted logs a WARNING: the WAL gap up to the new slot's creation LSN may be unrecoverable. Slot query is a short-lived libpq connection (`pg_walstream::PgReplicationConnection`) in `spawn_blocking` + timeout; query failure falls back to disk.
- Replay of the in-flight batch: a destination keeps a COMMIT it already received even when the client is SIGKILLed, while the checkpoint/LSN are persisted only after the commit, so a restart can re-apply a batch that is already committed. While `CdcClient` replays `sql_pending_tx/` at startup (always; there is no switch, and a genuine destination-side conflict inside the window is skipped too, logged at WARN; `TransactionManager::set_replay_grace(in_flight)`, spent per batch, so only the FIRST `in_flight` batches of the recovery skip duplicates: `GROUP_COMMIT_MAX_TXNS` (a crash can leave one whole group committed but unrecorded), because the consumer applies one transaction or group at a time in `commit_lsn` order; the budget is reset to 0 right after the recovery), a batch of ONLY inserts (`is_insert`) that fails with a duplicate-key error (`is_duplicate_key_error`: MySQL 1062, SQL Server 2627/2601, SQLite UNIQUE) is re-applied statement by statement and the duplicates are skipped (`replay_skipping_duplicates`); a batch with an UPDATE/DELETE keeps failing, because per-statement replay is not atomic and can undo the committed result. With the always-on fast path the in-flight transaction has no file and PostgreSQL re-sends it as live work, so `set_replay_grace` lets the first `GROUP_COMMIT_MAX_TXNS + 1` batches after recovery skip duplicates too (it is always the earliest transaction after the resume position; the grace is spent once per COMPLETED batch at `execute_batch_with_bulk_detection` (bulk loads included; a failed attempt, e.g. a connection error retried with backoff, or a failed group followed by its one-by-one retry, spends nothing), and is not granted right after a fresh snapshot nor when startup found no slot (a slot created now re-sends nothing, a duplicate there is a real conflict: `live_replay_grace`); a clean restart cannot be told from a crash, so a persistent "running" marker would be the next narrowing). Never widen these windows: a duplicate on the live path is a real error
- Shutdown coordination: `CancellationToken` + `oneshot` channel (producer -> consumer)
- Destinations behind `DestinationHandler` trait; Kafka uses event mode, SQL destinations use SQL batch mode
- Destinations are constructed via the per-Config registry (`Config::create_destination`). Built-ins self-register in `Config::default()`; external users add their own via `ConfigBuilder::custom_destination` (factory closure) or `ConfigBuilder::use_destination::<H>()` (for `H: Default`).
- `TransactionStorage` trait abstracts compressed vs uncompressed file I/O. Finalize passes the producer-tracked statement count through the trait (`write_transaction_from_file(path, known_count)` / `write_raw_lines_from_file`); uncompressed finalize does NO file re-read (compressed still reads to compress)
- `commit_transaction` returns `(PathBuf, TransactionFileMetadata)`; the producer builds the consumer notification from that in-memory metadata, never re-reading the `.meta` file it just wrote
- Statement-count invariant: producer-tracked `segment_statement_counts` is authoritative for `TransactionSegment.statement_count` and MUST equal what the consumer's `SqlStreamParser` reads back (it drives crash-resume segment-skip arithmetic). Events that render multiple `;`-statements (e.g. multi-table `TRUNCATE`) are counted via `count_rendered_statements`, which mirrors the parser in-memory — never `+= 1` per event
- Pending-transaction count is an in-memory `AtomicUsize` (`pending_tx_count`, `Ordering::Relaxed`), monitoring-only: seeded once at startup from the pending-dir scan, `+1` on commit, `-1` on finalize. Never gate control flow / LSN persistence on it
- MySQL uses one `mysql_async` pool for normal SQL batches and for LOAD DATA LOCAL INFILE
- SQL Server uses TDS Bulk Load (tiberius `bulk_insert`) for homogeneous INSERT batches, falls back to multi-value INSERT. On the live path it converts quoted integers to the column's integer type and requests `KEEP_NULLS` + `FIRE_TRIGGERS` + `CHECK_CONSTRAINTS` (always on, no setting); the snapshot's writers (`begin_snapshot_writes`) ask for `KEEP_NULLS` only
- Consumer detects homogeneous INSERT batches and routes to bulk insert path when threshold met
- Graceful shutdown invariant: every transaction the producer committed (including any it commits while shutting down) is applied before the process exits. `drain_and_shutdown` completes all queued transactions using an uncancellable token before persisting final LSN. The on-disk LSN represents the last FULLY APPLIED transaction. Recovery skips files with `commit_lsn <= flush_lsn`. Data not yet read from PostgreSQL stays in the slot and is not part of the guarantee.
- Never pass the main `CancellationToken` to `drain_and_shutdown` — it must use its own fresh (never-cancelled) token
- Shutdown ordering: when cancellation interrupts the consumer mid-apply it must `wait_for_producer` (keep receiving until the producer's oneshot or channel close, never stop receiving: a producer blocked on a full channel would deadlock) BEFORE the final drain. A failing destination is retried with the live backoff until everything is applied: neither the wait nor the drain has a timeout of its own, the process manager's stop timeout (SIGKILL) is the only bound (no env var, by design). Files of unapplied transactions stay in `sql_pending_tx/`
- A failed apply must clear the staged checkpoint of that file (`clear_staged_pending_progress`): the pre-commit hook stages it BEFORE the destination commits, and the shutdown flush would otherwise persist a checkpoint for a batch that was never applied (a restart would skip it: data loss)
- Group commit (ALWAYS on, no env var: the cap is the const `GROUP_COMMIT_MAX_TXNS` = 128 in `consumer.rs`, README "Group commit cap" has the sweep around it; `ConsumerSettings::group_commit_max_txns` carries it, `1` applies every transaction alone; `TransactionManager::process_transaction_group`): merges only transactions ALREADY queued (never waits: three transactions then silence commit at once, there is deliberately no flush timer and none is needed), consecutive in `commit_lsn` order, fresh (no resume checkpoint), whose total statement/event count is within `batch_size`. All-or-nothing in ONE destination batch with NO pre-commit hook (MySQL: a group never contains a TRUNCATE, which commits implicitly: `process_transaction_group` returns `Unsupported` and the transactions are applied one by one; SQL Server and SQLite roll a failed group back completely). DML coalescing (`coalesce_commands`) never puts an UPDATE into a CASE/JOIN statement together with an earlier UPDATE of a row it writes (same WHERE, or a WHERE the earlier SET values satisfy: REPLICA IDENTITY FULL chains, key changes), because every WHERE is evaluated against the rows as they were before the statement and the later value would be lost. MySQL assigns the SET columns left to right, so there an UPDATE that changes a column its WHERE reads while a LATER column is also changed is not coalesced either (a later CASE would read the new value and miss its row); on any error nothing changed and the consumer re-applies the same transactions one by one. After the destination commit: `record_applied_lsn` ONCE for the last `commit_lsn` (persisted BEFORE any file is deleted), then per-transaction cleanup. Event-mode destinations (Kafka) go through `DestinationHandler::execute_events_group_with_hook` (one delivery wait per group; Kafka is at-least-once, a failed group is re-sent one by one)
- In-memory fast path, APPROVED exception (2026-11-26; made always-on by the owner: no env var, the budget is the const `MEMORY_FAST_PATH_BUDGET_BYTES`, 64 MiB, in `transaction_manager.rs`): a normal (never streaming) transaction of at most `batch_size` statements that fits the byte budget lives only in memory (`mem-<tx>-<lsn>` virtual paths, `MemoryPayload`); it spills to the normal files the moment it exceeds one batch or the budget (never wait on the budget: the WAL reader must not stall). Safe because the slot only advances past a transaction after the consumer applied it (`flush_lsn` is updated by the consumer only), so a crash re-sends whatever was in memory. Therefore: never ACK ahead of apply, never keep a multi-batch transaction in memory (it needs the file checkpoint to resume), never let the fast path reorder (the consumer heap orders memory and file transactions by `commit_lsn`); a memory transaction that precedes a file transaction is first written to files (`persist_memory_payloads`), or recovery would apply the later file and raise the position past it, hiding the lost one from PostgreSQL's re-send
- **Initial snapshot (`pg2any-lib/src/snapshot/`), two APPROVED exceptions (2026-11-24)**: (1) the snapshot phase bypasses transaction files: rows flow reader -> `Batcher` -> byte-bounded channel -> N writer handlers -> destination. Phase 1 snapshots are non-resumable, so recovery is the marker file `snapshot_marker.json` (in `CDC_TRANSACTION_FILE_BASE_PATH`) + restart from scratch; everything after the `Completed` marker uses the normal file path. (2) `run_snapshot_phase` writes the LSN tracker exactly once, at completion, with `consistent_point`, AFTER the `Completed` marker is stored (`finalize_snapshot`); nothing is written during the copy. A crash between the two writes needs no repair: the slot's `confirmed_flush_lsn` (>= the consistent point) seeds the de-dup boundary in `reconcile_resume`, and the `Completed` marker holds only the slot name
- Snapshot startup is a pure decision (`decision::decide` -> Skip/Run/Resync/Recover/Fail) taken in `CdcClient::new` from marker + `pg_replication_slots` (`wal_status`, PG13+) + policy, and executed in `start_replication_from_lsn` BEFORE `init()`. The `InProgress` marker lists tables only after `prepare_targets` passed (so recovery never truncates tables a failed probe protected) and lists none under `append` (the tables may hold rows that are not ours, so a later policy switch must not truncate them); it also carries `copy_started`, false until just before the first row can be dispatched (a marker without the field counts as started), and `append` recovers only a marker whose copy never started. The marker is written durably (fsync of the file and of its directory) because a host crash must not bring back an older marker next to rows it never listed; automatic cleanup is limited to tables in our own marker and never under `append`; Kafka ignores the policy. Every await of the snapshot phase before the copy (slot creation, writer connects, `prepare_targets`, recovery clean-up) is raced against the cancel token by `cancellable`, so SIGTERM is honoured there too The `InProgress` marker also records the destination it wrote to (`sanitize_connection_string`, password masked) and `decide` refuses recovery at another destination, because recovery truncates the tables the marker lists
- `DestinationHandler` snapshot hooks (all defaulted): `snapshot_table_is_empty`, `snapshot_truncate_table`, `execute_snapshot_events_batch`, `set_snapshot_key_columns`, `max_snapshot_writers` (SQLite and Kafka = 1), `begin_snapshot_writes` (called once per writer before its first batch). A destination behaviour that is only valid for snapshot-rendered rows or only wanted for snapshot writers (MySQL failing the batch when `LOAD DATA LOCAL` skipped rows, which the live path only warns about; SQL Server leaving out `FIRE_TRIGGERS` + `CHECK_CONSTRAINTS` for its bulk copy) is switched via `begin_snapshot_writes` ONLY, never on the live path
- Snapshot byte budget: the reader holds ONE `ByteBudget` permit per batch and never waits for a second while holding one (FIFO semaphore, deadlock otherwise); an oversize batch is admitted alone. The budget is not a process memory cap: memory is flat vs table size, a single oversize row is amplified ~8-14x by the write path (README "Limits and performance")

- One destination handler serves the startup recovery and then the live consumer: `start_file_based_workflow` takes it out of `CdcClient`, recovers with it and hands it to the consumer, which closes it (`stop()` closes it only when it never got that far, so every early return puts it back). Connect + schema mappings + `max_rows_per_insert` is `Config::connect_destination`, shared with the snapshot's writers; do not copy that setup
- Startup order of the replication stream: `ensure_replication_slot()` BEFORE the startup recovery (a slot created afterwards starts behind everything committed meanwhile, which is lost when the slot had been deleted), `start()` AFTER it, right before the producer is spawned (nothing answers the walsender's keepalives until the producer polls, so a started stream is terminated after `wal_sender_timeout`; reproduced on PostgreSQL 15). `start_stream` replaces a stream whose idle connection died during the recovery with a fresh one that keeps the same `shared_lsn_feedback` (the consumer holds it). The three tests of the `recovery` module in `snapshot_e2e_sqlite.rs` (`make snapshot-test-sqlite`) pin all of this; the first fails if `start()` moves before the recovery, the second if the slot is created after it
- Consumer backlog and shutdown: while it backs off from a failing destination the consumer stops reading its channel at `MAX_QUEUED_TXNS_IN_BACKOFF` (10,000), so the channel fills and the producer waits (the WAL stays in the slot). A cancellation wakes it at once and it goes through `wait_for_producer`, which receives again: a producer blocked in `send` never reaches its own shutdown otherwise
- Source failure: when the producer's read of the stream fails for good (not a cancellation) it flushes, cancels the main token and returns the error; `CdcClient::stop` runs every step (join, ACK, close, persist the position) and returns the first error, so the process exits non-zero and a restart policy restarts it. Nothing may `expect` a task's `JoinHandle` in `stop()`
- A BEGIN for an open transaction id replaces it and returns the replaced one's memory budget (`release_replaced`)

## Important Files

- `pg2any-lib/src/client.rs` - Core orchestration logic, startup, recovery, shutdown
- `pg2any-lib/src/producer.rs` - WAL reader, transaction file writer (extracted from client.rs)
- `pg2any-lib/src/consumer.rs` - File executor, `ConsumerSettings`, group assembly (`extend_group`), `wait_for_producer`, drain_and_shutdown with retry, retry logic (extracted from client.rs)
- `pg2any-lib/src/transaction_manager.rs` - File-based transaction lifecycle + bulk insert routing + `analyze_transaction_content`. Also: `count_rendered_statements` (producer statement counting that mirrors the consumer parser), `pending_tx_count` monitoring counter
- `pg2any-lib/src/destinations/destination_factory.rs` - `DestinationHandler` trait definition
- `pg2any-lib/src/destinations/mysql.rs` - MySQL destination (mysql_async pool)
- `pg2any-lib/src/destinations/sqlserver.rs` - SQL Server destination (tiberius TDS Bulk Load)
- `pg2any-lib/src/destinations/common.rs` - Shared transaction helpers (`execute_with_hook_guard`, `commit_with_hook`)
- `pg2any-lib/src/destinations/bulk_insert.rs` - INSERT detection (backtick + bracket), TSV generation, multi-value INSERT fallback
- `pg2any-lib/src/destinations/coalescing.rs` - DML coalescing (multi-value INSERT, CASE-WHEN UPDATE)
- `pg2any-lib/src/config.rs` - All configuration fields and builder
- `pg2any-lib/src/env.rs` - Environment variable mapping (supports deprecated fallback names; `REMOVED_ENV_VARS` are ignored with a WARN). Settings read outside it and so env-only: `CDC_LAST_LSN_FILE` (`lsn_tracker.rs`), `PG2ANY_ENABLE_COMPRESSION` (`StorageFactory::from_env`), `CDC_KAFKA_*` (`kafka.rs`)
- `pg2any-lib/src/error.rs` - Error types (transient vs permanent classification matters for retry logic)
- `pg2any-lib/src/slot.rs` - Slot queries: `reconcile_resume`, `query_replication_slot` (`wal_lost`), `drop_replication_slot`, `query_replica_identity_keys` (Kafka snapshot keys)
- `pg2any-lib/src/snapshot/coordinator.rs` - `run_snapshot_phase`: clear previous attempt, slot snapshot, prepare targets, copy, `finalize_snapshot` (marker, then LSN tracker)
- `pg2any-lib/src/snapshot/decision.rs` - Pure startup decision (`decide`, `SnapshotAction`)
- `pg2any-lib/src/snapshot/marker.rs` - Versioned `snapshot_marker.json` (`SnapshotMarker`, `MarkerStore`); a corrupt file is an error, never "no snapshot"
- `pg2any-lib/src/snapshot/target.rs` - `prepare_targets`: probe every table first, then truncate per policy
- `pg2any-lib/src/snapshot/pipeline.rs` - `run_copy`: one reader, N writers, cancellation, first-error propagation
- `pg2any-lib/src/snapshot/budget.rs` - `ByteBudget` (1 KiB permits), `row_byte_estimate`
- `pg2any-lib/src/snapshot/batcher.rs` - `Batcher`: per-table batches bounded by rows and bytes (`BatchMode::Sql` via `render_insert_as_bulk`, `BatchMode::Events` for Kafka)

## Environment Variable Naming

- New canonical names: `CDC_CHANNEL_CAPACITY`, `CDC_BATCH_SIZE`
- Deprecated aliases (still work, emit warning): `CDC_BUFFER_SIZE`, `CDC_COMMIT_BATCH_SIZE`
- Use `parse_usize_env_with_fallback` pattern for any future renames
- Removed, ignored with a WARN so existing env files keep starting: `CDC_PROTOCOL_VERSION` (the protocol follows `CDC_STREAMING`: 2 when streaming, else 1), `CDC_BINARY_FORMAT`, `CDC_QUERY_TIMEOUT` (neither ever had an effect), `CDC_SQLSERVER_LIVE_BULK_LOAD` (its behaviour is always on). Group commit, the in-memory fast path, the shutdown drain and the SQL Server bulk load have no settings
- `load_config_from_env` returns `CdcError::Config` for a missing required variable or an unknown `CDC_DEST_TYPE` (it never panics or falls back). Its defaults differ from `Config::builder()` (slot `cdc_slot` vs `pg2any_slot`, publication `cdc_pub` vs `pg2any_pub`, streaming on vs off): do not change either without a migration note, a different slot name starts a new slot
- Snapshot (all new, no deprecated aliases): `CDC_INITIAL_SNAPSHOT` (`false`), `CDC_SNAPSHOT_TARGET_POLICY` (`fail_if_not_empty` | `truncate` | `append`, default `fail_if_not_empty`), `CDC_SNAPSHOT_WRITERS` (`4`), `CDC_SNAPSHOT_BUFFER_MB` (`16`), `CDC_SNAPSHOT_BATCH_ROWS` (`20000`). The three sizes come from throughput sweeps (`make snapshot-bench-*`): change them only with new measurements

## What NOT to Do

- Don't add `println!` - use `tracing` macros
- Don't bypass feature gates - respect `#[cfg(feature = "...")]` boundaries
- Don't add blocking I/O on the hot path - everything is async
- Don't modify LSN tracking from the producer - only the consumer updates `flush_lsn`
- Don't skip the file persistence step - it's the crash recovery mechanism (except the initial snapshot and the always-on in-memory fast path, see above)
- Don't increment `segment_statement_counts` by 1 per event - count via `count_rendered_statements` so it matches the consumer's `SqlStreamParser` (multi-statement events like multi-table TRUNCATE would otherwise corrupt crash-resume skip arithmetic)
- Don't re-read a transaction file at commit/finalize just to count or to fetch metadata you already hold in memory
- Don't write the LSN tracker during the snapshot copy or before the `Completed` marker is stored - only `finalize_snapshot` writes it, once
- Don't stage snapshot rows through transaction files, and don't extend the snapshot's file bypass to the live path
- Don't enable snapshot-only destination behaviour on the live path - gate it behind `begin_snapshot_writes`
- Don't apply a group commit with a pre-commit hook or a resume checkpoint, and don't delete a group's files before its LSN is persisted
- Don't keep a streaming or multi-batch transaction in memory, and don't wait on the memory budget (spill instead)
- Don't start the final shutdown drain while the producer may still send (see `wait_for_producer`)
